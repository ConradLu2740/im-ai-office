## 3. demo/MVP 的真相：单进程承载全部

完整架构（技术设计文档）是 OpenIM + Redis Streams + Postgres + 微服务；
**当前 MVP 是刻意简化的单机版**：

```
┌─────────────────────────────────────┐
│  桌面 .app（Tauri 壳 + 前端页面）     │
│         │ invoke / fetch             │
│  Python app.py（FastAPI，单进程）     │
│   ├─ core.py：意图/归属/记忆/任务/RBAC │  ← 10 个模块的"大脑"都在这一个文件
│   └─ openim_client.py：回写消息       │
│         │                            │
│  msg_gateway.cjs（Node，连 OpenIM WS）│
│         │                            │
│  OpenIM 服务端（Docker/Colima）       │
└─────────────────────────────────────┘
```

- **主链路文件**：`im-ai-office/app.py`（FastAPI 入口）+ `core.py`（全部业务逻辑）+ `openim_client.py`（回写）+ `desktop/src/msg_gateway.bundle.cjs`（网关）
- **辅助工具**：`cli.py`（headless 调试）、`test_flow.py`（回归测试）

> ⚠️ `services/` 目录还有一套 docker 微服务雏形（oim-webhook/ai-agent/board-api/reminder），是完整架构的早期形态，**当前不是主链路**（主链路走桌面端 app.py）。

## 4. 技术栈汇总

| 层 | 技术 | 用途 |
|---|---|---|
| 客户端 | Tauri 2 (Rust) | 桌面壳 |
| 前端 | 原生 HTML/CSS/JS | UI（MVP 未上框架） |
| 后端 | Python 3.9 + FastAPI + uvicorn | REST + 业务逻辑 |
| 数据 | SQLite（MVP）→ Postgres（完整版） | 任务/人/记忆/审计 |
| AI | DeepSeek LLM（OpenAI 兼容 API） | 意图识别/任务提取 |
| IM | OpenIM 3.8.3（Docker/Colima） | 消息管道 + WebSocket |
| 消息网关 | Node.js + @openim/client-sdk | 双工收发 |
| 调试工具 | cli.py / test_flow.py（Python） | 排障/回归 |

## 5. 未来拆分的路线（MVP 验证后）

| 拆什么 | 怎么拆 | 时机 |
|---|---|---|
| `core.py` → 独立服务 | ai-agent（意图/归属/记忆）+ board-api（任务）+ auth（RBAC）+ reminder（提醒） | 要上真团队时 |
| SQLite → Postgres | 表结构已在技术设计文档 §5 定义 | 同上 |
| 事件总线 | Redis Streams consumer group（代替进程内 EVENTS） | 多实例/可靠投递需求时 |
| 前端上框架 | React/Vue + 状态管理（MVP 原生够用） | UI 复杂度上来后 |

---

## 6. 一句话总结

> **现在的 demo/MVP = 1 个 Tauri 壳 + 1 个 FastAPI 单进程（内含 10 模块大脑）+ 1 个 Node 网关 + OpenIM**，闭环已全通（识别→消歧→确认→看板→汇总→审批→记忆），全部在 `im-ai-office/` 一个目录，`python3 app.py` 即可跑。
